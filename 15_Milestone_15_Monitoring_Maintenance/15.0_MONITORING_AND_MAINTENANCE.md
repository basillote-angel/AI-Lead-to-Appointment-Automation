# Milestone 15 — Monitoring and Maintenance

## Objective

Keep the Voryn production automation observable, healthy, secure, and maintainable after deployment. Monitoring should reveal lost leads, failed executions, delayed notifications, appointment issues, credential problems, and changes in business performance before they become customer-facing incidents.

Monitoring begins only after the production release gates in Milestones 12–14 are accepted. Until then, use the same checks in a controlled test environment.

## Current System Surface

Monitor these components:

- n8n workflow executions and failed nodes
- lead intake webhook availability and validation outcomes
- Supabase `leads` records and `automation_error_logs`
- Gemini analysis and response-draft failures
- Calendly polling, duplicate detection, booking state, and reminders
- Gmail/SMTP notifications and customer confirmations
- scheduled follow-up and appointment jobs
- credential expiry, quota, rate limits, and provider outages
- workflow exports, database backups, and restore readiness

## Monitoring Principles

1. Monitor business outcomes as well as technical uptime.
2. Alert on actionable conditions, not every normal execution.
3. Keep alerts separate from customer-facing messages.
4. Never place credentials or unsafe error text in dashboards or alerts.
5. Use stable identifiers such as lead ID, execution ID, and provider event ID.
6. Define an owner and response action for every alert.
7. Review trends on a schedule instead of relying only on real-time alerts.

## 15.0 Operational Metrics

### Lead funnel metrics

Track daily and weekly:

- leads received
- valid leads
- invalid leads
- duplicate submissions
- leads stored
- AI analyses completed
- AI analyses sent to manual review
- HOT, WARM, and NEEDS_INFORMATION counts
- approved responses
- follow-ups due and completed
- appointments invited
- appointments booked
- appointments cancelled or rescheduled
- confirmation delivery failures

### Reliability metrics

- total workflow executions
- failed executions
- failure rate by workflow and node
- retry count and exhausted retries
- average intake processing time
- average time from lead capture to approved response
- stale leads with no next action
- unmatched Calendly events
- duplicate provider events
- error-log write failures
- notification delivery failures

### Business metrics

- response rate
- qualification rate
- appointment booking rate
- booking rate by classification
- cancellation rate
- no-response rate
- time from inquiry to booking
- leads requiring manual review

Do not interpret a business metric without its time range, sample size, and source query.

## 15.1 Execution Monitoring

Use n8n execution history and the Error Trigger workflow to inspect:

- workflow name and version
- execution status
- failed node
- execution ID
- lead ID when available
- provider event ID when available
- retry count
- safe error category and message
- time of failure

Create a daily review for failed and waiting executions. Separate expected test failures from production incidents.

### Suggested alert thresholds

| Alert | Initial threshold | Action |
| --- | --- | --- |
| Lead intake failures | 3 failures in 15 minutes or 10% of submissions | Check n8n, webhook, validation, and Supabase |
| AI failures | 3 consecutive failures | Check Gemini quota, credentials, prompt/output validation |
| Calendly failures | 2 polling failures or one unmatched booking | Check provider access, query window, and lead matching |
| Email failures | 2 consecutive failures | Check Gmail/SMTP credential, quota, and recipient configuration |
| Error-log write failure | Any production occurrence | Use fallback alert and inspect database access |
| Stale follow-up | Any lead past its due time by the agreed SLA | Review lead and workflow state |
| Stale appointment | Any booked appointment without confirmation/reminder state | Reconcile Supabase with Calendly |

Tune thresholds after collecting baseline data. Do not use these starting values as final business SLAs.

## 15.2 Business and Data Monitoring

Create saved queries or views for operational review:

- leads created in the last 24 hours
- leads with `status` not updated within the expected SLA
- leads with `follow_up_required = true` and an overdue `next_follow_up`
- leads marked `BOOKED` without `appointment_status = BOOKED`
- appointments with missing date, time, or provider event ID
- duplicate or unmatched Calendly events
- open records in `automation_error_logs`
- error counts grouped by workflow, node, category, and day

Any query that exposes customer data must be access-controlled and minimized.

## 15.3 Alerts and Escalation

Every production alert should answer:

- What failed?
- When did it fail?
- Which workflow and node were involved?
- Which lead or provider event is affected?
- Is customer communication blocked?
- What is the immediate operator action?
- When should the issue be escalated?

Use this alert format:

```text
[VORYN AUTOMATION ALERT]
Severity:
System:
Workflow:
Node:
Occurred at:
Execution ID:
Lead ID:
Provider event ID:
Safe summary:
Customer impact:
Immediate action:
Owner:
```

Do not include API keys, tokens, passwords, authorization headers, or full customer payloads.

### Escalation levels

| Level | Condition | Response |
| --- | --- | --- |
| Informational | normal daily metric or resolved transient failure | record for review |
| Warning | repeated retry, overdue follow-up, stale appointment | owner reviews during operating hours |
| High | lead path, booking, confirmation, or database failure | notify owner promptly and create an incident record |
| Critical | secret exposure, data loss, false booking, or broad outage | disable affected path, preserve evidence, begin rollback |

## 15.4 Maintenance Schedule

### Each execution or alert

- inspect failed nodes and safe error details
- confirm affected business state
- verify retry or manual-review action
- avoid manually repeating a mutation without checking current state

### Daily

- review failed executions and open error logs
- review overdue follow-ups and stale appointments
- verify lead intake and notification activity
- check provider quota or rate-limit warnings

### Weekly

- review funnel and reliability metrics
- inspect duplicate and unmatched Calendly records
- verify backups completed
- review workflow changes and active workflow list
- close or escalate unresolved incidents

### Monthly

- test restore of a workflow and database backup
- review RLS, n8n access, and credential ownership
- review provider API changes and quotas
- rotate credentials according to the security policy
- review alert thresholds and operating SLAs
- update the runbook and contact list

### After every change

- export the accepted workflow version
- record the change, reason, owner, and rollback version
- run the relevant Milestone 13 regression tests
- confirm credentials and webhook configuration
- monitor the first production executions after activation

## 15.5 Credential and Provider Maintenance

Maintain an inventory without secret values:

```text
Credential/provider:
Purpose:
Environment:
Owner:
Expiration or rotation date:
Last tested:
Replacement procedure:
Failure symptom:
```

Before rotating a credential:

1. Confirm the replacement credential works in a controlled environment.
2. Record the intended change and rollback credential owner.
3. Update the n8n credential or secret store.
4. Run a safe provider health check.
5. Run the relevant workflow smoke test.
6. Revoke the old credential only after successful verification.

Never paste credentials into workflow exports, tickets, screenshots, or chat.

## 15.6 Backup and Recovery Maintenance

Verify:

- workflow exports are current and secret-free;
- schema and migration files match the deployed database;
- Supabase backups meet the agreed retention period;
- configuration inventories are current;
- backup storage access is restricted;
- restore instructions work for the current versions;
- recovery time and recovery point objectives remain realistic.

Record every restore test, including the result and any data discrepancy.

## 15.7 Incident Runbook

When a production incident occurs:

1. Identify the affected workflow, provider, node, lead IDs, and execution IDs.
2. Decide whether to pause intake, booking, reminders, or customer messaging.
3. Preserve logs and workflow versions.
4. Check whether the intended database mutation already happened.
5. Apply the documented retry, fallback, or rollback procedure.
6. Notify the owner and affected internal operators.
7. Reconcile lead, appointment, email, and provider states.
8. Run smoke and regression tests before reactivation.
9. Document root cause, impact, resolution, and prevention.

Do not delete evidence or repeatedly replay a failed execution without checking idempotency.

## Definition of Done

- [ ] Operational metrics and data sources are documented.
- [ ] n8n execution failures and open error logs are reviewed on a defined schedule.
- [ ] Alerts have thresholds, owners, actions, and escalation levels.
- [ ] Lead, follow-up, appointment, and notification health checks are available.
- [ ] Credential rotation and provider maintenance procedures are documented.
- [ ] Backup and restore checks are scheduled and recorded.
- [ ] Incident response and rollback procedures are accessible to the operator.
- [ ] Maintenance changes trigger the relevant regression tests.
- [ ] Monitoring does not expose secrets or unnecessary customer data.
