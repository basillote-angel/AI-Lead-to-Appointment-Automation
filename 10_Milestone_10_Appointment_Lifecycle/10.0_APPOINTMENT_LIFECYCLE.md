# Milestone 10 — Appointment Lifecycle

## Objective

Move an eligible lead from approved response to appointment booking, record the booking as the system of record, notify the team and customer, and stop follow-up when the appointment is confirmed.

The MVP uses **Calendly Free** for scheduling because it is the formal tool decision for this project. Google Calendar remains a later integration option, not a second booking path in the first implementation.

## Architecture Boundary

- n8n orchestrates the workflow and applies deterministic state changes.
- Calendly owns availability, invitee booking, time-zone presentation, rescheduling, and cancellation links.
- Supabase remains the lead and workflow record.
- The Calendly webhook is the source of truth for a completed booking; a generated booking link is not proof that an appointment exists.
- Customer-facing confirmation is sent only after the booking event is received and validated.

## Appointment States

Use `appointment_status` consistently:

| Value | Meaning |
| --- | --- |
| `NOT_SCHEDULED` | No booking link has been offered or no booking exists |
| `INVITED` | An approved response included the scheduling link |
| `BOOKED` | Calendly confirmed an appointment |
| `RESCHEDULED` | A previously booked appointment changed time |
| `CANCELLED` | The appointment was cancelled |
| `FAILED` | A booking event could not be processed and needs review |

The lead `status` should become `BOOKED` only after a valid Calendly booking event is processed. `RESPONDED` and `WAITING` must be added to the database status constraint before the follow-up workflow relies on them.

## Required Data

Existing lead fields:

- `lead_id`
- `name`
- `email`
- `phone`
- `appointment_date`
- `appointment_time`
- `calendar_event_id`
- `appointment_status`

Before implementation, confirm that the database or provider payload also preserves:

- provider event or invitee ID
- appointment time zone or UTC timestamp
- booking URL and cancellation/rescheduling URLs when available
- last appointment event received
- appointment update timestamp

Do not overwrite the lead's original contact data with untrusted webhook values without validating the event and matching the invitee email.

## Workflow

```text
Qualified lead
   ↓
Approved response with Calendly link
   ↓
Set appointment_status = INVITED
   ↓
Calendly booking
   ↓
Calendly webhook to n8n
   ↓
Validate event and match invitee
   ├── invalid → Milestone 11 error path
   └── valid → update lead to BOOKED
                    ↓
             send confirmation
                    ↓
             schedule reminder
```

## Step 1 — Configure the scheduling link

1. Create one Voryn appointment event type in Calendly.
2. Set the available days, duration, buffer, minimum notice, and business time zone.
3. Use a test event type or short availability window while learning.
4. Store the public scheduling URL as configuration, not in credentials or source code.
5. Include the lead email or a stable lead reference where Calendly supports it, so the webhook can be matched deterministically.

Do not ask n8n to calculate availability in the MVP. Calendly is responsible for preventing double booking.

## Step 2 — Offer the booking link

After human approval of the response:

1. Verify the lead is eligible for scheduling (`HOT` or `WARM`, depending on the business rule).
2. Confirm the response does not claim that an appointment already exists.
3. Update `appointment_status` to `INVITED`.
4. Send or display the approved Calendly link.
5. Keep the lead status as `CONTACTED` or `WAITING` until Calendly confirms a booking.

## Step 3 — Receive and validate the booking webhook

Configure the Calendly webhook to call a dedicated n8n Webhook node. For each event:

1. Verify the webhook secret or signature when available.
2. Confirm the event type is supported.
3. Extract the provider event ID, invitee email, start time, end time, and time zone.
4. Match the invitee to exactly one lead by normalized email or a stable lead reference.
5. Reject or escalate unmatched, duplicate, malformed, or already-processed events.
6. Process the event idempotently using the provider event ID.

Supported first-version events are booking created, booking rescheduled, and booking cancelled. The exact Calendly event names must be confirmed from the current API/webhook payload during implementation.

## Step 4 — Update the lead

For a valid booking:

- set `status` to `BOOKED`
- set `appointment_status` to `BOOKED`
- save the provider event ID in `calendar_event_id`
- save the appointment date and time in the agreed time zone
- set `follow_up_required` to `false`
- clear or ignore `next_follow_up`
- update `updated_at`

For rescheduling, update the appointment values and use `RESCHEDULED` as the event audit state before returning the lead to `BOOKED` if the provider confirms the new booking. For cancellation, set `CANCELLED` and route the lead for human review or a new scheduling invitation.

## Step 5 — Confirmation and reminders

After the database update succeeds:

1. Notify the internal team with the lead, appointment time zone, provider event ID, and action.
2. Send the approved customer confirmation with the time zone and rescheduling/cancellation links.
3. Create a 24-hour reminder using an n8n Wait node or scheduled query.
4. Optionally create a 1-hour reminder only after the 24-hour path is reliable.
5. Before each reminder, re-read the lead and stop if the appointment is cancelled or rescheduled.

The reminder must use the stored appointment time, not the time when the workflow executed.

## Test Checklist

### Test 1 — Link offered

Expected:

- The approved response contains the Calendly URL.
- `appointment_status` becomes `INVITED`.
- The lead is not marked `BOOKED`.

### Test 2 — Booking created

Expected:

- A valid webhook matches one lead.
- Appointment fields and provider ID are stored.
- Lead status becomes `BOOKED`.
- Follow-up is stopped.
- One internal and one customer confirmation are sent.

### Test 3 — Duplicate booking event

Expected:

- The provider event ID is recognized as already processed.
- No duplicate confirmation or reminder is created.
- The workflow records the duplicate safely.

### Test 4 — Reschedule and cancellation

Expected:

- Rescheduling updates the stored appointment time.
- Cancellation stops reminders and does not leave the lead falsely marked as booked.

### Test 5 — Invalid or unmatched webhook

Expected:

- No lead is updated.
- The event is logged and sent to the Milestone 11 manual-review path.

### Test 6 — Time zone

Expected:

- The confirmation clearly identifies the appointment time zone.
- A reminder fires at the intended instant, regardless of n8n server time.

## Definition of Done

- [ ] Calendly event type and scheduling URL are configured securely.
- [ ] Qualified leads receive an approved scheduling invitation.
- [ ] `INVITED`, `BOOKED`, `RESCHEDULED`, and `CANCELLED` behavior is defined.
- [ ] Calendly webhook events are validated and matched idempotently.
- [ ] Appointment details and provider ID are stored.
- [ ] Booking stops follow-up.
- [ ] Confirmation is sent only after a successful database update.
- [ ] A 24-hour reminder is tested and cancellation-aware.
- [ ] Duplicate, unmatched, malformed, rescheduled, cancelled, and time-zone cases are tested.
