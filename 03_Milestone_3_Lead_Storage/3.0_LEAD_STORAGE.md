# Milestone 3 — Lead Storage

## Objective

Store each valid lead in a persistent database so the record survives after an n8n execution ends.

This milestone teaches:

- Tables and columns
- PostgreSQL data types
- Primary keys
- Unique constraints
- Database credentials
- Mapping n8n data into a database row

## Design Decision

The project uses Supabase, which provides a hosted PostgreSQL database. We will store only leads that have already passed Milestone 2 validation.

The `email` column is unique. This gives us a first layer of duplicate protection: the same normalized email cannot be inserted twice.

## Step 1 — Create the Supabase table

1. Create or open your Supabase project.
2. Open **SQL Editor**.
3. Open `01_create_leads_table.sql` from this folder.
4. Copy and run the SQL.
5. Open **Table Editor** and confirm that the `leads` table exists.

Do not put API keys, passwords, or database URLs in this repository.

## Step 2 — Update the n8n workflow

The workflow will become:

```text
Webhook
   ↓
Code — Validate and Normalize
   ↓
IF — Is Valid?
   ├── true  → Supabase — Insert Lead → Respond to Webhook
   └── false ─────────────────────────→ Respond to Webhook
```

The IF node is important. It prevents invalid leads from reaching the database.

## Step 3 — Add the IF node

1. Add an **If** node after the Code node.
2. Create a Boolean condition.
3. Set the left value to the expression:

```text
{{ $json.valid }}
```

4. Set the operation to **is true**.
5. Connect the true output to the Supabase node.
6. Connect the false output directly to the Respond to Webhook node.

Invalid leads should still receive the validation error response from Milestone 2.

## Step 4 — Add Supabase credentials

In n8n:

1. Add a **Supabase** node, or use an **HTTP Request** node if your n8n version does not provide a Supabase node.
2. Create credentials using n8n's credential manager.
3. Never paste secrets into a Code node or a committed workflow export.

For a first local learning setup, use the Supabase project URL and the appropriate API credential in n8n's credential form. Use the least-privileged credential available for the operation.

## Step 5 — Configure the insert

Configure the Supabase node to insert one row into the `leads` table.

Map these fields from the Code node:

| Database column | n8n expression |
| --- | --- |
| name | `{{ $json.lead.name }}` |
| email | `{{ $json.lead.email }}` |
| phone | `{{ $json.lead.phone }}` |
| company | `{{ $json.lead.company }}` |
| service | `{{ $json.lead.service }}` |
| budget | `{{ $json.lead.budget }}` |
| timeline | `{{ $json.lead.timeline }}` |
| message | `{{ $json.lead.message }}` |
| status | `NEW` |

Do not map `lead_id`, `created_at`, or `updated_at`; PostgreSQL supplies those defaults.

## Step 6 — Handle duplicate emails

The database unique constraint rejects a second row with the same email.

For this first version, connect the Supabase error path to a human notification or a response explaining that the lead already exists. Do not silently discard the error.

A later improvement can search for the email first and update the existing record instead of returning an insert error.

## Test Checklist

### Test 1 — Valid lead

Use the Maria Santos lead.

Expected:

- IF node takes the true path.
- Supabase inserts one row.
- The row has status `NEW`.
- The response is successful.

### Test 2 — Invalid lead

Use an empty message or invalid email.

Expected:

- IF node takes the false path.
- Supabase is not executed.
- HTTP response is `400`.
- No invalid row appears in `leads`.

### Test 3 — Duplicate email

Submit the same valid email twice.

Expected:

- First submission inserts one row.
- Second submission does not create a second row.
- The duplicate condition is visible for handling.

## Definition of Done

- [ ] Supabase `leads` table exists.
- [ ] Valid leads are inserted.
- [ ] Invalid leads bypass storage.
- [ ] Database-generated ID and timestamps are present.
- [ ] Duplicate email behavior is understood and visible.
- [ ] No credentials are committed to Git.
