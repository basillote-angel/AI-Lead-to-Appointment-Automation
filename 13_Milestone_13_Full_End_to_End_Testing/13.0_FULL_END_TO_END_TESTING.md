# Milestone 13 — Full End-to-End Testing

## Objective

Prove that the Voryn lead-to-appointment workflow behaves correctly from intake through follow-up, booking, confirmation, reminder, failure handling, and security boundaries.

Testing is evidence-based. A test is not complete until the expected result, actual result, evidence location, and defect or resolution are recorded.

## Current Test Gate

Milestone 13 depends on the current Milestone 12 security review and the correction of known Milestone 10 and 11 defects.

The supplied workflow exports currently have these expected defects:

- the appointment update uses `=calendar_event_id` instead of `calendar_event_id`;
- follow-up scheduling and waiting use different test intervals;
- the follow-up branch does not demonstrate repeated cycles or maximum-count escalation;
- the error handler logs raw error text without sanitization;
- the error handler logging and alert paths are sequential;
- Calendly rescheduling and cancellation paths are not implemented in the supplied graph;
- the reminder delay is a short test delay rather than an appointment-time-based reminder.

These defects must be recorded as failed tests until corrected and retested.

## Test Environment

Use a dedicated test configuration:

- local n8n instance
- test Supabase project or clearly labeled test rows
- test Gmail recipient and test customer addresses
- Calendly test event type or controlled availability
- Gemini test credential and known test prompts
- no real customer data
- no production credentials

Record the workflow version, database migration version, test date, timezone, and tester for every test run.

## Test Record

Use this record for every case:

```text
Test ID:
Date/time:
Workflow version:
Database/schema version:
Timezone:
Input or setup:
Expected result:
Actual result:
Evidence:
Status: PASS / FAIL / BLOCKED

```

Evidence may include an n8n execution ID, sanitized database row, email subject/body, Calendly event ID, screenshot, or exported test response. Do not include credentials or full sensitive payloads in evidence.

## Defect Severity

| Severity | Meaning | Release rule |
| --- | --- | --- |
| Critical | Secret exposure, data loss, duplicate customer message, false booking, or unsafe access | Must fix before any end-to-end pass |
| High | Broken lead path, failed appointment state, missing failure alert, or silent workflow stop | Must fix before milestone completion |
| Medium | Incomplete retry, reminder, reporting, or edge-case behavior | Track and assign before production |
| Low | Documentation, wording, or non-blocking usability issue | May be deferred with rationale |

## Definition of Done

- [ ] Test environment and test data are isolated from production.
- [ ] Every test has an expected result, actual result, evidence, and status.
- [ ] Normal, HOT, WARM, NEEDS_INFORMATION, invalid, and duplicate paths pass.
- [ ] Human approval, response, no-response, follow-up, and closed paths pass.
- [ ] Booking, confirmation, reminder, cancellation, and rescheduling paths pass.
- [ ] AI, Supabase, Calendly, Gmail, rate-limit, credential, and Error Trigger failures are tested.
- [ ] Security and export checks pass.
- [ ] Critical and high defects are corrected and retested.
- [ ] A final test report is stored with the project documentation.
