# Milestone 14 — Production Deployment

## Objective

Move the tested Voryn automation from local development to a controlled production environment without exposing credentials, losing leads, duplicating appointments, or silently changing workflow behavior.

Production deployment is not a substitute for testing. It begins only after the Milestone 12 security evidence and Milestone 13 test report have accepted the remaining defects.

## Current Deployment Baseline

The current MVP uses:

- n8n for workflow orchestration
- Supabase/PostgreSQL for lead and error-log storage
- Gemini for lead analysis and response drafting
- Calendly Free for scheduling
- Gmail/SMTP for internal and customer email
- a browser lead form calling the n8n webhook
- Calendly polling for appointment discovery in the supplied export

The current development environment is local n8n. No production host, production domain, production webhook, or production credential set is assumed to exist yet.

## Release Gates

Do not deploy until all of these are true:

- [ ] Milestone 12 security decisions and evidence are documented.
- [ ] Milestone 13 critical and high tests pass.
- [ ] The `calendar_event_id` field-name defect is corrected and retested.
- [ ] Follow-up timing and repeat-cycle behavior are corrected and retested.
- [ ] Error-message sanitization and independent alert fallback are tested.
- [ ] Calendly duplicate, cancellation, and rescheduling behavior is defined and tested.
- [ ] Reminder timing is based on the appointment time, not a short test delay.
- [ ] A production backup and restore rehearsal is complete.
- [ ] A rollback version of every active workflow is stored.

If a gate is incomplete, keep the system in test or staged mode.

## Target Production Architecture

```text
Customer browser
      ↓ HTTPS
Production lead form
      ↓ authenticated or protected webhook
Production n8n
      ├── Supabase production project
      ├── Gemini production credential
      ├── Calendly production configuration
      ├── Gmail/SMTP production credential
      └── Error and notification paths
```

The production design should keep the orchestration layer, database, AI provider, scheduling provider, and email provider separately identifiable so an incident can be isolated and recovered.

## 14.0 Production Architecture

Choose the simplest hosting arrangement that meets the tested requirements:

### Option A — Managed n8n

Use a managed n8n service when the priority is reduced server administration, HTTPS, updates, and operational simplicity. Confirm plan limits, execution retention, credential storage, webhook URL, and export/restore capabilities before purchase.

### Option B — Self-hosted n8n on a secured VPS

Use a VPS only when the project requires deployment control or cost predictability. The host must have HTTPS, firewall rules, restricted administration, persistent storage, backups, monitoring, and a documented update process.

Do not expose the n8n editor or database administration interfaces publicly without access control.

## 14.1 Hosting and Runtime Setup

Before importing workflows:

1. Provision the production host or managed n8n workspace.
2. Configure a stable HTTPS URL.
3. Enable n8n authentication and restrict editor access.
4. Configure timezone explicitly and document it.
5. Configure persistent execution data and workflow storage.
6. Set resource and execution limits appropriate to expected lead volume.
7. Confirm the host clock and timezone are correct.
8. Verify that the production webhook URL is reachable over HTTPS.
9. Confirm that failed executions can be inspected by an authorized operator.

Do not copy the local n8n data directory into production without reviewing credentials, executions, ownership, and sensitive data.

## 14.2 Production Credentials and Configuration

Create separate production credentials for:

- Supabase production database/API access
- Gemini production access
- Calendly production access
- Gmail or SMTP production sending
- n8n encryption and administrative access

Use the n8n credential manager or the host's secret store. Never put secret values in workflow Code nodes, browser JavaScript, Git, README files, screenshots, or test evidence.

Maintain a configuration inventory without secret values:

```text
Setting:
Purpose:
Environment: TEST / STAGING / PRODUCTION
Owner:
Rotation interval:
Last verified:
Rollback or replacement procedure:
```

Production credentials must not be used during local testing.

## 14.3 Database and Data Migration

1. Create or select a dedicated Supabase production project.
2. Apply the reviewed schema and migrations.
3. Confirm the canonical lead status values.
4. Confirm appointment fields and `automation_error_logs` exist.
5. Review RLS and database permissions before accepting traffic.
6. Create indexes and constraints required by the tested workflow.
7. Insert one clearly labeled health-check record only if the test plan permits it.
8. Verify that no test leads or credentials were copied into production.

The production database must preserve the uniqueness and idempotency rules used by intake and Calendly processing.

## 14.4 Workflow Promotion

Promote workflows through environments in this order:

```text
Local development
      ↓
Staging or controlled test
      ↓
Production import
      ↓
Credential reassignment
      ↓
Configuration review
      ↓
Activation
```

Before activation:

- compare the exported workflow version with the accepted test version;
- confirm the Error Trigger workflow ID and relationship;
- replace test email recipients with approved production recipients;
- verify Calendly user and event configuration;
- verify all Supabase table and field IDs;
- confirm retry and timeout settings;
- disable test-only delays and test branches;
- confirm only the intended workflows are active.

Do not activate a workflow immediately after import without inspecting its credentials, webhook path, nodes, and connections.

## 14.5 Production Webhooks

The test webhook path is `voryn-lead`. Production must use a deliberate HTTPS endpoint and documented protection decision.

Before switching the form:

1. Create or import the production webhook workflow.
2. Configure authentication, signing, origin controls, or an equivalent protection where appropriate.
3. Keep secrets out of browser-visible code.
4. Configure request-size and input limits.
5. Confirm invalid requests return the intended HTTP response.
6. Send a synthetic health-check request.
7. Confirm the request reaches the production workflow and database.
8. Update the form only after the production endpoint passes the smoke test.
9. Keep the old endpoint disabled or clearly marked as test-only.

For the current Calendly polling design, document the polling interval, query window, duplicate protection, and provider credential. If a Calendly webhook is introduced later, treat it as a separate tested integration.

## 14.6 Backups and Restore

Back up before deployment and before schema changes:

- workflow exports without embedded secrets
- SQL schema and migrations
- configuration inventory without secret values
- test report and accepted release version
- operational documentation
- Supabase data according to the selected plan and retention policy

A backup is not complete until restore is tested. Record:

```text
Backup date:
Backup contents:
Storage location:
Encryption/access control:
Restore owner:
Restore steps:
Restore result:
Recovery time:
Recovery point:
```

Never treat screenshots or an untested workflow export as the only recovery method.

## 14.7 Smoke Test After Deployment

Run these tests immediately after activation using isolated data:

| ID | Test | Expected result |
| --- | --- | --- |
| DEP-01 | Health-check webhook | HTTPS endpoint responds correctly |
| DEP-02 | Valid synthetic lead | Lead is stored once and reaches the expected workflow state |
| DEP-03 | Invalid synthetic lead | Request is rejected without storage or customer email |
| DEP-04 | Internal alert | Approved test recipient receives the notification |
| DEP-05 | Calendly polling | Test booking is matched to the intended lead only once |
| DEP-06 | Error Trigger | Controlled failure creates a safe log and operator alert |
| DEP-07 | Backup verification | Current workflow and database recovery artifacts are available |
| DEP-08 | Rollback rehearsal | Previous accepted workflow version can be restored |

Record n8n execution IDs, sanitized database evidence, email evidence, and provider event IDs.

## 14.8 Rollback Plan

Rollback when a deployment causes data loss, false booking, duplicate customer communication, credential exposure, or an unacceptable failure rate.

1. Disable the affected production workflow.
2. Stop or disable the production form endpoint if intake cannot be trusted.
3. Preserve execution IDs, error logs, and affected lead IDs.
4. Restore the last accepted workflow version.
5. Reassign the verified production credentials.
6. Restore database data only when the incident requires it and the restore point is known.
7. Re-run smoke tests.
8. Notify the owner and affected internal operators.
9. Document the incident and corrective action before reactivation.

Do not delete failure evidence during rollback.

## Definition of Done

- [ ] Production architecture and hosting decision are documented.
- [ ] HTTPS and n8n access control are configured.
- [ ] Production credentials are separate from test credentials.
- [ ] Production Supabase schema, permissions, and migrations are verified.
- [ ] Accepted workflows are promoted without test-only configuration.
- [ ] Production webhook protection and URL are tested.
- [ ] Calendly production configuration and polling or webhook behavior are documented.
- [ ] Backups are created, protected, and restored in a test.
- [ ] Post-deployment smoke tests pass.
- [ ] Rollback is rehearsed and documented.
- [ ] Production deployment evidence is stored without secrets.
