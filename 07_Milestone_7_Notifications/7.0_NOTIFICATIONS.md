# Milestone 7 — Notifications

## Objective

Notify the Voryn team when an important lead event occurs, including the lead details, qualification, route, AI summary, and recommended action.

This milestone sends internal notifications. It does not send customer-facing responses; those belong to Milestone 8 and later follow-up work.

## Architecture Boundary

- Validation remains deterministic and belongs to Milestone 2.
- Storage remains the source of truth and belongs to Milestone 3.
- AI interpretation belongs to Milestone 4.
- Scoring belongs to Milestone 5.
- Routing belongs to Milestone 6.
- Notifications inform the team but do not change qualification.
- Do not send sensitive credentials or unnecessary private data in notification text.

## Notification Rules

| Route | Notification priority | Recommended content |
| --- | --- | --- |
| `PRIORITY` | High | Lead details, score, summary, and appointment recommendation |
| `FOLLOW_UP` | Normal | Lead details, missing information, and follow-up action |
| `INFORMATION_REQUEST` | Normal | Lead details, information gaps, and clarification action |
| `MANUAL_REVIEW` | High | Reason for escalation and link to the lead record |

## Workflow

Continue after the Milestone 6 route nodes:

```text
Set Priority Route
Set Follow-Up Route
Set Information Request Route
Set Manual Review Route
          ↓
Notification node
          ↓
Continue to response or inspection
```

For the first implementation, each route may connect to its own notification node or to one shared notification node. Keep the existing invalid-lead path unchanged.

## Step 1 — Choose a notification channel

Use one channel available to you, such as email, Slack, or a simple internal webhook. For a beginner-friendly local test, email or a notification service with an n8n credential is appropriate.

Store credentials in n8n's credential manager. Never place API keys, passwords, or private webhook URLs in this repository.

## Step 2 — Build the notification message

Include only useful operational information:

```text
Voryn Lead Alert

Name: {{ $json.name }}
Company: {{ $json.company }}
Email: {{ $json.email }}
Service: {{ $json.service }}
Budget: {{ $json.budget }}
Timeline: {{ $json.timeline }}
Lead score: {{ $json.lead_score }}
Classification: {{ $json.lead_classification }}
Route: {{ $json.route }}
Recommended action: {{ $json.next_action }}
AI summary: {{ $json.ai_summary }}
Missing information: {{ $json.missing_information }}
```

Use the expression picker if the route node preserves the data under a different path. Do not invent values when a field is empty.

## Step 3 — Configure route-specific priority

If your notification node supports a subject or priority, use:

- `HOT` / `PRIORITY`: `Urgent Voryn lead requires attention`
- `WARM` / `FOLLOW_UP`: `Voryn lead needs follow-up`
- `NEEDS_INFORMATION`: `Voryn lead needs more information`
- `MANUAL_REVIEW`: `Voryn lead requires manual review`

## Test Checklist

### Test 1 — HOT notification

Use a lead classified as `HOT`.

Expected:

- One internal notification is sent.
- It includes the score, classification, route, and recommended action.
- The original lead data remains unchanged.

### Test 2 — WARM notification

Use the Maria Santos result if it is classified as `WARM` because information is missing.

Expected:

- One follow-up notification is sent.
- Missing information is visible.
- The notification does not send a customer-facing message.

### Test 3 — NEEDS_INFORMATION notification

Use a vague lead.

Expected:

- One information-request notification is sent.
- The team can see what details are missing.

### Test 4 — Manual review notification

Use an unexpected or missing classification.

Expected:

- One escalation notification is sent.
- The reason for manual review is visible.
- No automatic customer-facing message is sent.

### Test 5 — Invalid lead

Submit an invalid lead.

Expected:

- The existing validation response is returned.
- No qualification or route notification is sent.

## Definition of Done

- [ ] A notification channel is configured securely in n8n.
- [ ] HOT leads notify the team with high priority.
- [ ] WARM leads notify the team about follow-up.
- [ ] NEEDS_INFORMATION leads notify the team about missing information.
- [ ] Manual-review cases notify the team visibly.
- [ ] Notifications include score, classification, route, and recommended action.
- [ ] Invalid leads do not trigger route notifications.
- [ ] Notifications do not make qualification decisions.
- [ ] No customer-facing response is sent automatically.
