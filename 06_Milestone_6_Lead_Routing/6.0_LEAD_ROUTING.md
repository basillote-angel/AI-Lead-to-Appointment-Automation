# Milestone 6 — Lead Routing

## Objective

Route each classified lead to the correct next action without changing the score or qualification decision.

Milestone 5 decides the classification. Milestone 6 decides what should happen next.

## Architecture Boundary

- Validation belongs to Milestone 2.
- Storage belongs to Milestone 3.
- AI interpretation belongs to Milestone 4.
- Scoring and classification belong to Milestone 5.
- Routing belongs to Milestone 6.
- Do not ask AI to choose the route.
- Do not recalculate or overwrite `lead_score` or `lead_classification`.
- Invalid leads keep the existing Milestone 3 path and bypass routing.

## Routing Rules

| Classification | Route | Recommended action |
| --- | --- | --- |
| `HOT` | Priority | Notify the team and offer the appointment path quickly |
| `WARM` | Follow-up | Request missing details and continue follow-up |
| `NEEDS_INFORMATION` | Information request | Ask for the details needed to assess fit |

These routes are workflow labels, not final sales decisions.

## Workflow

Continue after the Milestone 5 qualification update:

```text
Supabase — Update Qualification
   ↓
Switch — Route by Classification
   ├── HOT → Priority action
   ├── WARM → Follow-up action
   └── NEEDS_INFORMATION → Information request
```

Keep the invalid lead path unchanged:

```text
Invalid lead → Existing validation response
```

## Step 1 — Add the Switch node

1. Add a **Switch** node after **Supabase — Update Qualification**.
2. Set the value to the classification from the current item. Use the expression picker to select the actual field path, such as:

```text
{{ $json.lead_classification }}
```

3. Create three rules:

```text
is equal to HOT
is equal to WARM
is equal to NEEDS_INFORMATION
```

4. Name the outputs `HOT`, `WARM`, and `NEEDS_INFORMATION` if your n8n version allows output labels.
5. Add a fallback output for an unexpected or missing classification.

## Step 2 — Configure route actions

For this milestone, use a **Set** or **Edit Fields** node on each branch. Add these fields:

### HOT branch

```json
{
  "route": "PRIORITY",
  "next_action": "Contact promptly and offer appointment booking"
}
```

### WARM branch

```json
{
  "route": "FOLLOW_UP",
  "next_action": "Request missing information and follow up"
}
```

### NEEDS_INFORMATION branch

```json
{
  "route": "INFORMATION_REQUEST",
  "next_action": "Ask the lead for information needed to assess fit"
}
```

Do not replace the lead's original data, AI analysis, score, or classification. Add routing metadata alongside the existing fields.

## Step 3 — Handle the fallback route

Unexpected classifications should not disappear silently. Connect the fallback output to a human escalation or an error notification with a message such as:

```text
Lead classification is missing or not recognized. Manual review required.
```

Do not automatically send a customer-facing message from the fallback route.

## Step 4 — Continue to the next milestone

For now, connect each route to a temporary inspection or response node so you can verify the result. Customer notifications belong to Milestone 7, response drafting belongs to Milestone 8, and follow-up automation belongs to Milestone 9.

## Test Checklist

### Test 1 — HOT lead

Use the Maria Santos lead and its completed qualification result.

Expected:

- Switch selects `HOT`.
- The priority route is produced.
- `lead_score` and `lead_classification` remain unchanged.
- The original lead and AI analysis remain intact.

### Test 2 — WARM lead

Use a supported service with some missing information.

Expected:

- Switch selects `WARM`.
- The follow-up route is produced.
- The lead is not rejected.

### Test 3 — NEEDS_INFORMATION lead

Use a vague lead with insufficient information.

Expected:

- Switch selects `NEEDS_INFORMATION`.
- The information-request route is produced.
- The lead remains available for clarification.

### Test 4 — Invalid lead

Submit an empty required field or invalid email.

Expected:

- The existing validation response is returned.
- The lead does not reach Supabase qualification or the Switch node.

### Test 5 — Unexpected classification

Use a controlled test value such as `UNKNOWN`.

Expected:

- The fallback route runs.
- A human-review or error action is visible.
- No customer-facing message is sent automatically.

## Definition of Done

- [ ] Switch node routes `HOT`, `WARM`, and `NEEDS_INFORMATION`.
- [ ] HOT produces a priority route.
- [ ] WARM produces a follow-up route.
- [ ] NEEDS_INFORMATION produces an information-request route.
- [ ] Unexpected classifications use a visible fallback path.
- [ ] Invalid leads bypass routing.
- [ ] Original lead data, AI analysis, score, and classification remain unchanged.
- [ ] Routing does not use an AI decision.
- [ ] Each route has been tested.
